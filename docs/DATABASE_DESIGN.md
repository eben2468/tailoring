# Database Design — Nutɔfe

> Status: **Implemented as SQL, verified on MySQL 8.4.11 (Docker) — awaiting approval.**
> Authoritative source: [`database/migrations/`](../database/migrations/). Generated snapshot: [`database/schema/schema.sql`](../database/schema/schema.sql).
> Approved inputs (2026-10-07): offline support · no workers · no payments · GHS · Africa/Accra · Docker · VPS · Gemini (free tier).

---

## 1. Design Principles

1. **Ledgers are the source of truth; totals are calculated.** Actual hours come from `work_logs`, stock on hand from `inventory_transactions`, last/next maintenance from `tool_maintenance_logs`. Nothing that can be calculated safely is stored twice (views in §9).
2. **History is never destroyed.** Measurement sets are immutable; work logs and stock transactions are voided, not deleted; business records use tombstones (`deleted_at`).
3. **Offline-ready.** Business records have device-generatable UUIDv7 keys, a `version` for conflict detection, a `sync_seq` change cursor, and tombstones.
4. **Configuration is data.** Measurement fields, task types, job types, task templates and categories are rows the owner can extend, so nothing is hardcoded.
5. **The database guards integrity as the last line of defence.** Foreign keys, `CHECK` constraints, unique keys and generated columns enforce the rules the API also validates.
6. **No unnecessary tables.** Suppliers are text on the item, stock reservations are not modelled, and the AI chat tables are deferred to the AI phase (§12).

## 3. Key, Timestamp & Audit Strategy

### 3.1 Three kinds of tables
| Kind | Primary key | Extra columns | Tables |
|---|---|---|---|
| **Business records** (created online or offline, synced) | `id BINARY(16)` UUIDv7, generated by the app or API | `version`, `sync_seq`, `created_by`, `updated_by`, `created_at`, `updated_at`, `deleted_at` | customers, measurement_sets, jobs, job_tasks, job_task_checklist_items, work_logs, appointments, inventory_items, inventory_transactions, tools, tool_maintenance_logs, files |
| **Configuration** (owner-editable, online only) | `SMALLINT`/`INT UNSIGNED AUTO_INCREMENT` + stable `code` | `is_active`, `sort_order`, `created_at`, `updated_at` | measurement_groups, measurement_fields, task_types, job_types, job_type_task_templates, inventory_categories, tool_categories |
| **System / server-generated** | `BIGINT UNSIGNED AUTO_INCREMENT` or natural key | as needed | users, user_sessions, settings, counters, audit_logs, notifications, ai_predictions, ai_insights; `user_devices` uses the device's UUID |

`measurement_values` has a natural composite key `(measurement_set_id, field_id)`. Its rows are immutable children of a set.

UUIDs are stored as `BINARY(16)` **without byte swapping** (UUIDv7 is already time-ordered, so inserts stay index-friendly). In SQL use `UUID_TO_BIN(x)` / `BIN_TO_UUID(x)` with no swap flag.

### 3.2 Timestamps
- `created_at` / `updated_at` / `*_at`: `DATETIME(3)` in **UTC**, defaulted and maintained by MySQL (`DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)`). The server runs with `default-time-zone=+00:00`, and every API connection runs `SET time_zone='+00:00'`.
- `DATETIME` is used rather than `TIMESTAMP`, because it has no 2038 limit and no implicit timezone conversion.
- Business dates (`order_date`, `due_date`, `collection_date`, `purchase_date`, `performed_on`) are `DATE` values in the business timezone (`settings.business.timezone` = `Africa/Accra`, UTC+0 with no DST, but never assume that).
- Work and stock events carry the time they **happened** (`started_at`, `occurred_at`), which can be earlier than `created_at` when they were recorded offline.

### 3.3 Audit fields
- Every business record has `created_by` (NOT NULL) and `updated_by` → `users.id`.
- `version` increments on every update. A device sends the version it edited; a mismatch means a conflict (HTTP 409).
- Sensitive actions (logins, voids, stock adjustments, measurement corrections, settings and admin actions) also write an `audit_logs` row with before/after JSON, device and request id.

### 3.4 Sync columns (offline support)
- `sync_seq`: the value of `counters('sync')` at the row's last write. The API increments the counter **inside the writing transaction** (`UPDATE counters SET counter_value = LAST_INSERT_ID(counter_value + 1) WHERE counter_key = 'sync'`). That row lock serialises writers, so `sync_seq` order equals commit order, and devices pull `WHERE sync_seq > :cursor` without ever missing a row. `sync_seq` has no default, so an insert that forgets it fails.
- `deleted_at`: a tombstone so deletions reach every device. Rows are kept (not purged).
- Configuration tables are not synced row by row. Any configuration change increments `counters('config_version')`, and devices re-download the whole configuration bundle.
- Job numbers are assigned by the server from `counters('job_number')`. A job created offline has `job_number = NULL` until it syncs.

## 4. Entity-Relationship Description

```
users ─1:N─ user_devices ─1:N─ user_sessions
users ─1:N─ notifications, audit_logs;  users ─1:N─ (created_by/updated_by of every business record)

measurement_groups ─1:N─ measurement_fields ─1:N─ measurement_values ─N:1─ measurement_sets ─N:1─ customers
measurement_sets ─0..1:N─ measurement_sets (supersedes_set_id: correction chain)

job_types ─1:N─ job_type_task_templates ─N:1─ task_types
customers ─1:N─ jobs ─N:1─ job_types
jobs ─N:0..1─ measurement_sets  (composite FK (measurement_set_id, customer_id): same customer only)
jobs ─1:N─ job_tasks ─N:1─ task_types
job_tasks ─1:N─ job_task_checklist_items
job_tasks ─1:N─ work_logs ─N:0..1─ user_devices

appointments ─N:0..1─ customers, jobs, job_tasks

inventory_categories ─1:N─ inventory_items ─1:N─ inventory_transactions ─N:0..1─ jobs (usage history)
tool_categories ─1:N─ tools ─1:N─ tool_maintenance_logs

files ─N:0..1─ customers | jobs | inventory_items | tools   (at most one owner)
ai_predictions ─N:0..1─ jobs | job_tasks | inventory_items
ai_insights → (entity_type, entity_id) soft reference;  settings, counters: standalone
```

**Cardinality notes**
- A customer has many measurement sets. "Current measurements" are the latest value of each field across all of that customer's sets.
- A job belongs to one customer and one job type, and it may reference the measurement set it was cut from.
- A job has many tasks, a task has many work logs, and at most **one running work log per user** exists across the whole database.
- A stock transaction may reference the job that used the material.

## 6. Tables in Detail

Legend: **PK** primary key · **FK** foreign key (target, on delete) · **UQ** unique · **IX** index · **CK** check. "Sync block" = `version INT UNSIGNED`, `sync_seq BIGINT UNSIGNED`, `created_by`/`updated_by BIGINT UNSIGNED → users`, `created_at`/`updated_at`/`deleted_at DATETIME(3)`.
Unless stated otherwise, every FK is `ON DELETE NO ACTION` (restrict) and `ON UPDATE NO ACTION`. Keys are immutable, so cascading updates are never needed.

### 6.1 System

**users**: PK `id BIGINT`; `full_name VARCHAR(120)`, `email VARCHAR(190)` **UQ** (case-insensitive collation), `phone`, `password_hash VARCHAR(255)` (Argon2id), `role ENUM('owner','admin')`, `is_active`, `preferences JSON` (UI, notification toggles, quiet hours), `failed_login_count`, `locked_until`, `last_login_at`, `password_changed_at`, timestamps. Users are deactivated, never deleted.

**user_devices**: PK `id BINARY(16)` (installation id generated on the device); FK `user_id → users`; `device_name`, `platform ENUM('android','ios')`, `app_version`, `fcm_token` **UQ**, `last_synced_at`, `last_seen_at`, `revoked_at`, timestamps.

**user_sessions**: PK `id BIGINT`; FK `user_id → users`, `device_id → user_devices (SET NULL)`; `family_id BINARY(16)` **IX**, `access_token_hash BINARY(32)` **UQ**, `access_expires_at`, `refresh_token_hash BINARY(32)` **UQ**, `refresh_expires_at`, `ip_address VARBINARY(16)`, `user_agent`, `last_used_at`, `revoked_at`, `revoke_reason ENUM(…)`, `created_at`. **IX** `(user_id, revoked_at)`. **CK** refresh expiry ≥ access expiry.

**settings**: PK `setting_key VARCHAR(80)`; `setting_value JSON`, `description`, FK `updated_by → users`, `updated_at`. Seeded keys: `business.name` (Nutɔfe), `business.timezone` (Africa/Accra), `business.currency` (GHS), `business.currency_symbol` (GH₵), `business.phone_region` (GH), `business.logo_file_id`, `measurements.default_unit` (in), `schedule.working_hours`, `schedule.capacity_hours_per_day`, `jobs.number_format`, `jobs.due_soon_days`, `timer.long_running_alert_hours`, `timer.review_threshold_hours`, `tools.maintenance_due_soon_days`, `notifications.digest_time`, `ai.enabled`, `ai.provider` (gemini), `ai.min_samples_for_estimate`.

**counters**: PK `counter_key VARCHAR(60)`; `counter_value BIGINT UNSIGNED`. Rows `sync`, `config_version`, `job_number` are created by the migration.

**audit_logs**: PK `id BIGINT`; FK `user_id → users`, `device_id → user_devices (SET NULL)`; `action VARCHAR(60)`, `entity_type`, `entity_id VARCHAR(36)` (holds both UUIDs and integers), `changes JSON`, `ip_address`, `request_id`, `created_at`. **IX** `(entity_type, entity_id)`, `(user_id, created_at)`, `(created_at)`.

### 6.2 Configuration

**measurement_groups**: PK `id SMALLINT`; `code` **UQ**, `group_name`, `sort_order`, `is_active`, timestamps.

**measurement_fields**: PK `id INT`; FK `group_id → measurement_groups`; `code VARCHAR(50)` **UQ** (stable identifier for reports and AI), `label`, `value_type ENUM('length','text','choice')`, `choice_options JSON`, `min_cm`/`max_cm DECIMAL(7,3)`, `help_text`, `sort_order`, `is_active`, timestamps. **IX** `(group_id, sort_order)`. **CK**: max > min; ranges only on length fields; `choice_options` present ⇔ `value_type = choice`. Seeded with the 16 fields from the brief plus the design's extras (half back, front length, bottom opening, shoulder slope, posture, blade prominence, trouser break, fit notes).

**task_types**: PK `id SMALLINT`; `code` **UQ**, `type_name`, `kind ENUM('work','milestone')`, `is_fitting`, `color_key`, `sort_order`, `is_active`, timestamps. Seeded: measurement, cutting, sewing, fitting, alteration, finishing, pressing, quality_check (work) and ready_for_collection, completed (milestones with no hours). New types are new rows.

**job_types**: PK `id SMALLINT`; `code` **UQ**, `type_name` **UQ**, `description`, `components`, `default_quantity` (**CK** 1–999), `sort_order`, `is_active`, timestamps. Seeded: 3-piece suit, 2-piece suit, blazer, shirt, trousers, kaftan, agbada, alteration.

**job_type_task_templates** (task templates): PK `id INT`; FK `job_type_id → job_types (CASCADE)`, `task_type_id → task_types`; `task_name` (optional override), `sort_order`, `default_estimated_seconds` (**CK** ≤ 500 h), timestamps. **UQ** `(job_type_id, sort_order)`. Copied into `job_tasks` when a job is created, so editing a template never changes existing jobs.

**inventory_categories** / **tool_categories**: PK `id SMALLINT`; `category_name` **UQ**, `sort_order`, `is_active`, timestamps.

### 6.3 Customers & measurements

**customers**: PK `id BINARY(16)`; `full_name VARCHAR(150)`, `phone` (E.164, **not** unique, because families share phones), `phone_alt`, `email`, `address`, `notes`, `style_preferences`, `preferred_unit ENUM('in','cm')`, `archived_at`, sync block. **IX** `full_name`, `phone`, `sync_seq`.

**measurement_sets**: PK `id BINARY(16)`; FK `customer_id → customers`, `supersedes_set_id → measurement_sets`; `measured_at DATETIME(3)`, `entered_unit ENUM('in','cm')`, `notes` (posture notes), sync block. **UQ** `(id, customer_id)` (the target of the jobs composite FK). **IX** `(customer_id, measured_at)`. **CK** a set cannot supersede itself.

**measurement_values**: PK `(measurement_set_id, field_id)`; FK `measurement_set_id → measurement_sets (CASCADE)`, `field_id → measurement_fields`; `value_cm DECIMAL(7,3)`, `value_text VARCHAR(255)`. **CK** exactly one of `value_cm` / `value_text`; `value_cm > 0`.

#### How measurement history works
1. Every measuring session inserts a **new** `measurement_sets` row and its values. Existing sets are never updated; the API exposes no update endpoint for them.
2. A set may be **partial**: remeasuring only the waist creates a set with one value.
3. **Current measurements** (`v_customer_current_measurements`) = for each field, the value from the most recent set that contains it. Verified: Kofi's waist shows 34.25 in from the newest partial set, while his other fields come from the full set before it.
4. **Corrections** (a value recorded wrongly) are a new set with `supersedes_set_id` pointing at the set it corrects; both remain visible in history. A set entered by mistake can be tombstoned (`deleted_at`), which hides it but keeps it.
5. Values are stored in **centimetres** with 3 decimals, so inches round-trip exactly to 2 decimals (18.75 in → 47.625 cm → 18.75 in). `entered_unit` records what the tailor used.
6. Jobs reference the set they were made from, and the composite FK guarantees it belongs to the same customer. That set can never be removed while jobs reference it.

### 6.4 Production

**jobs**: PK `id BINARY(16)`; `job_number VARCHAR(20)` **UQ** (NULL until assigned); FK `customer_id → customers`, `job_type_id → job_types`, `(measurement_set_id, customer_id) → measurement_sets(id, customer_id)`; `title`, `description`, `quantity` (**CK** 1–999), `priority ENUM('normal','high','urgent')`, `status ENUM('draft','queued','in_progress','on_hold','ready_for_collection','completed','cancelled')`, `order_date`, `due_date` (**CK** ≥ order_date), `collection_date` (**CK** ≥ order_date), `fabric_note`, `progress_override DECIMAL(5,2)` (**CK** 0–100), `notes`, `cancel_reason`, `completed_at` (**CK** required when status = completed), sync block. **IX** `(status, due_date)`, `due_date`, `(customer_id, order_date)`, `job_type_id`, `completed_at`, `sync_seq`. **No hour columns** (see `v_job_hours`).

**job_tasks**: PK `id BINARY(16)`; FK `job_id → jobs (CASCADE)`, `task_type_id → task_types`; `task_name`, `sort_order`, `status ENUM('pending','in_progress','completed','skipped')`, `estimated_seconds` (**CK** ≤ 500 h), `progress_override` (**CK** 0–100), `scheduled_start`/`scheduled_end` (planned calendar block, **CK** end > start), `completed_at` (**CK** required when completed), `notes`, sync block. **IX** `(job_id, sort_order)`, `task_type_id`, `status`, `scheduled_start`, `sync_seq`. A task's actual start and end come from its work logs (`v_task_hours.actual_start/actual_end`). Job deletion cascades to tasks only if the tasks have no work logs, because `work_logs` restricts.

**job_task_checklist_items**: PK `id BINARY(16)`; FK `job_task_id → job_tasks (CASCADE)`; `label`, `is_done`, `done_at` (**CK** required when done), `sort_order`, sync block.

**work_logs** (the labour ledger): PK `id BINARY(16)`; FK `job_task_id → job_tasks`, `device_id → user_devices`; `entry_type ENUM('timer','manual')`, `started_at`, `ended_at` (NULL = running), **`duration_seconds` GENERATED** = `TIMESTAMPDIFF(SECOND, started_at, ended_at)`, `note`, `needs_review`, `void_reason` (**CK** only on voided rows), **`running_user_id` GENERATED** = `created_by` while running, sync block. **UQ** `running_user_id` enforces one running timer per user. **CK** `ended_at > started_at`; manual entries must have an end. **IX** `(job_task_id, started_at)`, `started_at`, `sync_seq`.
Pausing closes the row and resuming creates a new one. Corrections void the row (`deleted_at` + `void_reason`) and add a new entry.

### 6.5 Scheduling & appointments
**appointments**: PK `id BINARY(16)`; FK `customer_id → customers`, `job_id → jobs (SET NULL)`, `job_task_id → job_tasks (SET NULL)`; `appointment_type ENUM('fitting','consultation','measurement','collection','delivery','other')`, `title`, `starts_at`, `ends_at` (**CK** > starts_at), `location`, `status ENUM('scheduled','confirmed','completed','cancelled','no_show')`, `reminder_minutes_before` (**CK** ≤ 7 days), `notes`, sync block. **IX** `starts_at`, `(customer_id, starts_at)`, `job_id`, `job_task_id`, `sync_seq`.
**Scheduling** of production work uses `job_tasks.scheduled_start/end`. The calendar combines appointments, task blocks, `jobs.due_date`/`collection_date` and `v_tool_maintenance_status.next_maintenance_date` with queries, so no calendar data is duplicated.

### 6.6 Inventory
**inventory_items**: PK `id BINARY(16)`; FK `category_id → inventory_categories`; `item_name`, `sku` **UQ**, `description`, `unit ENUM('m','yd','cm','pcs','spool','cone','roll','set','box','pack','kg','g')`, `min_stock_level` (**CK** ≥ 0), `reorder_quantity` (**CK** > 0), `unit_cost DECIMAL(12,2)` (optional, GHS, **CK** ≥ 0), `supplier_name`, `supplier_contact`, `storage_location`, `notes`, `archived_at`, sync block. **No quantity column.**

**inventory_transactions** (stock ledger): PK `id BINARY(16)`; FK `item_id → inventory_items`, `job_id → jobs`; `transaction_type`, `quantity_change DECIMAL(12,3)` (signed), `unit_cost`, `reference`, `note`, `occurred_at`, `void_reason`, sync block. **IX** `(item_id, occurred_at)`, `job_id`, `(transaction_type, occurred_at)`, `sync_seq`.

| Requirement | Transaction type | Sign (**CK**) |
|---|---|---|
| Opening balance | `opening` | + |
| Stock addition | `purchase`, `return` (unused material back) | + |
| Stock reduction | `usage` (optionally linked to a job = usage history), `write_off` | − |
| Stock adjustment | `adjustment` (stock-count correction) | ± (≠ 0) |

**CK** `job_id` is only allowed on `usage`/`return`. Stock on hand = `SUM(quantity_change)` of non-voided rows (`v_inventory_stock`). The DB does **not** forbid a negative balance, because usage recorded offline must be accepted. The API blocks it for online writes and raises a `negative_stock` notification when a synced write causes it.

### 6.7 Tools
**tools**: PK `id BINARY(16)`; FK `category_id → tool_categories`; `tool_name`, `brand_model`, `serial_number`, `purchase_date`, `tool_condition ENUM('excellent','good','fair','poor')`, `operational_status ENUM('operational','needs_service','out_of_service','retired')`, `storage_location`, `maintenance_interval_days` (**CK** 1–3650; NULL = no schedule), `next_maintenance_override DATE`, `notes`, `archived_at`, sync block. Cost columns were dropped (no payments).

**tool_maintenance_logs**: PK `id BINARY(16)`; FK `tool_id → tools`; `performed_on DATE`, `maintenance_type ENUM('routine','repair','calibration','inspection','sharpening','cleaning','other')`, `description`, `performed_by` (text), `condition_after`, sync block. **IX** `(tool_id, performed_on)`.
**Next maintenance** = `next_maintenance_override`, otherwise (last maintenance, else purchase date, else created date) + interval. Logging maintenance clears the override and updates `tool_condition` (an API rule).

### 6.8 Files, notifications, AI
**files**: PK `id BINARY(16)`; optional FKs `customer_id`, `job_id`, `inventory_item_id`, `tool_id` (**CK** at most one set); `file_kind`, `caption`, `original_name`, `mime_type`, `size_bytes`, `width_px`, `height_px`, `sha256 BINARY(32)`, `storage_key` **UQ** (NULL until the binary is uploaded), `upload_status ENUM('pending','stored','failed')` (**CK** stored ⇒ key present), sync block.

**notifications**: PK `id BIGINT`; FK `user_id → users`; `notification_type`, `severity`, `title`, `body`, `entity_type`, `entity_id`, `route`, `dedupe_key`, `read_at`, `push_status`, `push_attempts`, `pushed_at`, `sync_seq`, timestamps. **UQ** `(user_id, dedupe_key)` means each condition alerts once per period. **IX** `(user_id, read_at, created_at)`, `(push_status, created_at)`.

**ai_predictions**: PK `id BIGINT`; FK `job_id`, `job_task_id`, `inventory_item_id` (all CASCADE, because they are derived data); `prediction_type ENUM('task_hours','job_hours','completion_date','delay_risk','stockout_date')`, `predicted_seconds` / `predicted_date` / `predicted_score` (**CK** at least one), `confidence` (**CK** 0–100), `sample_size`, `method` (e.g. `stats-median-v1`, `gemini-…`), `explanation`, `inputs_hash`, `created_at`. Actual outcomes are **not** copied in: accuracy is measured by joining to `v_task_hours`, `jobs.completed_at` and `v_inventory_stock`.

**ai_insights**: PK `id BIGINT`; `insight_type`, `severity`, `title`, `body`, `payload JSON` (evidence and proposed action), `entity_type`/`entity_id`, `insight_status ENUM('new','seen','applied','dismissed','expired')`, `method`, `inputs_hash`, `generated_at`, `expires_at`, `acted_at`, FK `acted_by → users`, `sync_seq`, `updated_at`. **UQ** `(insight_type, inputs_hash)` means the same insight is never stored twice.

## 7. Delete / Update Behaviour Summary

| Relationship | On delete | Why |
|---|---|---|
| measurement_values → measurement_sets | CASCADE | Values are part of the set |
| job_tasks → jobs | CASCADE | Tasks are part of the job; blocked anyway if work logs exist |
| job_task_checklist_items → job_tasks | CASCADE | Part of the task |
| job_type_task_templates → job_types | CASCADE | Part of the job type |
| appointments → jobs / job_tasks | SET NULL | The appointment still happened |
| user_sessions / audit_logs → user_devices | SET NULL | Keep the record if a device is removed |
| ai_predictions → jobs / job_tasks / inventory_items | CASCADE | Derived data |
| **Everything else** | NO ACTION (restrict) | Protects history: work logs, stock, measurements, customers and users can never be removed through a cascade |

In practice business rows are tombstoned (`deleted_at`) rather than hard-deleted; the only hard deletes are of unsynced drafts. `ON UPDATE` is never needed because keys never change.

## 8. Index Strategy
- Every FK column is indexed (InnoDB requires it). Composite indexes match the main screens:
  - `jobs (status, due_date)`: dashboard counters, jobs filters, overdue
  - `job_tasks (job_id, sort_order)`: job detail
  - `job_tasks (scheduled_start)` and `appointments (starts_at)`: calendar ranges
  - `work_logs (job_task_id, started_at)` and `work_logs (started_at)`: hours per task, reports by period
  - `inventory_transactions (item_id, occurred_at)`: stock per item
  - `measurement_sets (customer_id, measured_at)`: measurement history
  - `notifications (user_id, read_at, created_at)`: bell badge and list
- `sync_seq` is indexed on every synced table, for the pull query.
- The views use `LATERAL` joins, so per-row aggregation goes through these indexes. When filtered to one job, `v_job_hours` collapses to a primary-key lookup (checked with EXPLAIN).

## 9. Calculated Values (Views)

| View | Columns | Rules |
|---|---|---|
| `v_task_hours` | estimated, actual, remaining, overrun (seconds); calculated and effective progress; is_progress_manual; actual_start/end; is_running; log_count | actual = Σ closed, non-voided logs. remaining = max(est − actual, 0), and 0 when completed or skipped. progress = 100 if completed, else override, else min(actual/est × 100, **99**), else 0 |
| `v_job_hours` | estimated, actual, remaining, overrun; task and completed counts; progress; has_running_timer; actual_start | Work tasks only (milestones ignored). Skipped tasks add no estimate. remaining = **Σ task remaining**. progress = override, else 100 when ready or completed, else estimate-weighted task progress, else completed-task ratio |
| `v_inventory_stock` | quantity_on_hand; is_low_stock (≤ min); is_out_of_stock (≤ 0); is_negative; last_transaction_at | Σ quantity_change of non-voided transactions |
| `v_tool_maintenance_status` | last_maintenance_date, maintenance_count, next_maintenance_date | override, else (last, purchase or created date) + interval |
| `v_customer_current_measurements` | latest value per customer and field, plus its set, date and unit | ROW_NUMBER over sets, newest first |

Date-dependent flags (overdue, due today, maintenance due soon) need the business-local "today", so the API computes them from these columns.

**Verified on MySQL 8.4.11:**

| Case | Est | Actual | Remaining | Progress |
|---|---|---|---|---|
| Brief example | 12 h | 7 h | **5 h** | **58.33 %** |
| Overrun, not finished | 2 h | 3 h | 0 h (overrun 1 h) | 99 % |
| Completed under estimate | 4 h | 1 h | 0 h | 100 % |
| Manual override 40 % | 5 h | 0 h | 5 h | 40 % (manual) |
| Skipped | 3 h | 0 | 0 | excluded from the job |
| Voided log (10 h) | — | not counted | — | — |
| **Job total** | 23 h | 11 h | **10 h** (not 23 − 11 = 12) | 65.13 % |

Performance: these views calculate on read. At this business's scale (thousands of jobs) that is cheap. If it ever becomes slow, the fix is a cached column maintained in the same transaction, which is a later optimisation and not needed now.

## 10. Transactions (API rules)

These operations must run in one transaction, together with the `sync` counter increment and the audit row:

| Operation | Contents |
|---|---|
| Create job | Assign job number (`counters` row lock), insert job, copy template rows into `job_tasks`, optional fitting appointments |
| Start timer | Lock the user's running log (the unique key also guards this), insert work log, set task to `in_progress`, set job `queued` → `in_progress` |
| Stop / switch timer | Close the log, optionally complete the task, optionally start the next log |
| Complete task / job | Status plus `completed_at`, status-machine check |
| Stock usage / adjustment | `SELECT … FOR UPDATE` on the item row, compute balance, check for negative stock (online), insert transaction, low-stock notification |
| Log maintenance | Insert log, clear `next_maintenance_override`, update `tool_condition` |
| Record measurements | Insert set and all its values |
| Sync push (from a device) | All changes in one batch are applied per record with version checks; conflicts are reported, never silently overwritten |

Isolation level: `READ COMMITTED` (set on the server) with explicit row locks where noted above.

## 14. Questionable Assumptions (please confirm)
1. **Offline conflicts** are detected by `version` and resolved by the owner; there is no silent last-write-wins. Configuration edits require a connection.
2. **Offline timers use the phone's clock.** Device times are checked on sync (not in the future, not overlapping); sessions over 12 h are flagged `needs_review`.
3. **One running timer per user** (with no workers, the owner times one task at a time). If the owner needs to time two tasks at once, the unique key changes to one running timer per task.
4. **Negative stock is allowed** at the DB level (offline reality) and raised as an alert.
5. **"Ready for Collection" and "Completed" exist twice**: as zero-hour milestone task types (so they appear on the job timeline as in the design) and as job statuses. The **job status** is authoritative.
6. **Progress is capped at 99 % until a task is marked complete.**
7. **Partial measurement sets and the "latest value per field" rule** for current measurements.
8. **Inventory unit cost is kept as optional data** ("cost if required" in the brief); it is not a payment feature. Remove it if you prefer.
9. **Template hours are placeholders**: the owner should give real typical hours per garment.
10. **Job numbers** continue as plain numbers padded to 3 digits (`#024`) and never reset. Should they reset every year (e.g. `#2026-024`)?
11. **Phone numbers are not unique** per customer, and duplicate customers are possible. Should the app warn on a matching phone?
